# Quotes Search Engine

A small Python search tool for `quotes.toscrape.com`. It crawls the
site, builds an inverted index, and answers single or multi-word
queries from the command line.

## Requirements

- Python 3.10 or newer
- `requests`, `beautifulsoup4` for the crawler
- `pytest`, `pytest-cov` for the test suite

Install everything in one go:

```
pip install -r requirements.txt
```

## Quick start

```
git clone <repo-url>
cd quotes-search-engine
pip install -r requirements.txt
python src/main.py build
```

The crawler waits 6 seconds between requests,
so a full run of ~150 pages takes about 15 minutes. While developing,
cap it with `--max-pages`:

```
python src/main.py build --max-pages 10
```

## Commands

The tool has four subcommands. Every read command accepts `--input` to
point at a different index file (`build` accepts `--output` for the
same reason). The default path is `data/index.json`.

### `build` - crawl and index

```
python src/main.py build
python src/main.py build --max-pages 20 --output data/small.json
```

Crawls the seed site, indexes each page as it's downloaded, and writes
the resulting index to JSON. The default seed is
`https://quotes.toscrape.com/`.

### `load` - load and summarise

```
python src/main.py load
```

Reads an index from disk and prints how many unique terms it has and
how many term-document postings it contains. Useful as a quick sanity
check that a build produced something reasonable.

### `print` - show the entry for one word

```
python src/main.py print love
```

Sample output:

```
'love': 14 occurrence(s) across 8 page(s)
  https://quotes.toscrape.com/
    freq=2, positions=[145, 312]
  https://quotes.toscrape.com/page/2/
    freq=1, positions=[87]
  ...
```

The lookup word is tokenised the same way as the indexer, so
`print Love`, `print "love."`, and `print love` all hit the same entry.

### `find` - multi-word search

```
python src/main.py find love
python src/main.py find life death
python src/main.py find "don't"
```

Returns pages that contain **all** of the query words, ranked by total
frequency across the query terms. If the query gets normalised
differently from what you typed (`Good!` → `good`, `don't` → `don, t`),
the tool tells you so the results aren't surprising.

A query containing `'` usually needs quoting in the shell - otherwise
the apostrophe breaks shell tokenising before Python ever sees it.

# Testing Strategy

This document explains the approach taken to testing the search tool -
what's tested, why, how to run it, and what's not covered.

## Approach

Tests are organised into five files, each focused on a single module:

- `test_crawler.py` - the crawler (link extraction, fetching, the crawl loop)
- `test_indexer.py` - tokenisation, the inverted index, and persistence
- `test_search.py` - the `find` and `print_word` functions
- `test_main.py` - the CLI layer (argparse wiring and command handlers)
- `test_integration.py` - end-to-end tests wiring the real components together

The split between unit and integration tests is deliberate. Unit tests mock
their dependencies and assert on isolated behaviour, which makes failures
easy to localise. Integration tests use the real crawler, indexer, and
search code together (only the network is mocked), which proves the system
works as a whole; bugs in how the pieces fit together don't always show
up in unit tests.

## Why we mock the network

The target site (`quotes.toscrape.com`) is a real third-party service. Tests
that hit it would be:

- **Slow** - the politeness window alone is 6 seconds per page, so even a
  small crawl would take half a minute per test run.
- **Flaky** - network failures, rate limiting, or the site going down would
  cause unrelated test failures.
- **Rude** - running the full test suite repeatedly during development
  would hammer a site that exists for educational scraping, not load testing.

Instead, `requests.get` and `crawler.fetch_page` are patched to return
canned HTML for known URLs. `time.sleep` is also patched so the politeness
delay doesn't slow tests down - but assertions still verify it would have
been called with the right value in production.

## What we didn't test

A few things were considered and consciously left out:

- **Performance.** The brief specifies correctness, not throughput. A
  performance test would be flaky (depends on the runner's speed) and
  doesn't earn any rubric marks.
- **The `if __name__ == "__main__":` blocks** in `crawler.py` and
  `indexer.py`. These exist for ad-hoc manual testing during development;
  they're not part of the public interface.

These gaps are visible in the coverage report.

## Tools used

- **pytest** as the test runner — chosen over `unittest` for its concise
  assertion style and built-in fixtures (`tmp_path`, `capsys`).
- **unittest.mock** (standard library) for patching `requests.get` and
  `time.sleep` in crawler tests.
- **pytest-cov** for line coverage reporting.

## Design notes

A few decisions worth flagging:

**Tokenisation.** `re.sub(r"[^a-z0-9]+", " ", text).split()` after
lowercasing. Strips punctuation, keeps numbers, doesn't preserve
apostrophes — so `don't` becomes the two tokens `don` and `t`. A bit
odd in isolation, but it's consistent between the indexer and search
so queries don't silently miss things.

**Politeness window.** Fixed at 6 seconds. The crawler also sleeps
after a *failed* fetch, since it still hit the server.

**URL normalisation.** `/tag/foo/page/1/` collapses to `/tag/foo/`,
and `#fragments` are stripped before deduplication. Without these
the crawler would index the same content twice.

**Skip suffixes.** `/login` and `/logout` aren't followed — there's
nothing useful to index there, and visiting `/logout` would throw away
any session state for the rest of the crawl.

**Ranking in `find`.** Pages are sorted by sum of TF-IDF scores across
the query terms (`tf × log(N/df)`), ties broken alphabetically by URL.
This rewards pages where rare query terms appear often, rather than
pages that just happen to be wordy. IDF is computed on the fly from
the loaded index - no separate file format change needed.

**Index format.** JSON, three levels deep:
`{term: {url: {"freq": int, "positions": [int]}}}`. Storing positions
costs disk space but leaves phrase queries on the table for later.
